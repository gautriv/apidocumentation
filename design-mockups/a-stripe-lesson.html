Writing docs for LLMs.

It's 4 p.m. on a Thursday, friend. A developer Slacks you: "hey what does 429 mean again 😅". You answer them in five seconds. Now imagine that same question, three thousand times a day, asked by an agent.

The good news: writing for LLMs is mostly just writing well, with the dial turned up on a few specific things. Predictable structure. Errors that contain the recovery action. No ironic asides about how flaky the rate-limiter is.

The slightly harder news is that "writing well" is the part most teams skip, because the API ships first and the docs ship "soon." So this lesson is going to feel like it's about LLMs, and it kind of is, but really it's about a discipline you should have had anyway.

Why this matters #

When a human reads a 429, they see "oh I got rate-limited, let me retry in a minute." When an agent reads a 429, it sees — whatever your error description literally says. If you wrote "Request limited", congratulations: the agent now thinks the request itself was malformed and won't retry.

The Greenfield rule #

Here's how we document the same error in the Greenfield Library API, before and after. Try toggling the language tabs.

$ curl https://api.greenfield.lib/v1/books/42 \
    -H "Authorization: Bearer $TOKEN"

HTTP/2 429 Too Many Requests
Retry-After: 30
Content-Type: application/json

{
  "error": "rate_limited",
  "message": "You've made 100 requests in 60s; ceiling is 60.",
  "retry_after_seconds": 30,
  "docs": "https://docs.greenfield.lib/errors/rate_limited"
}
const res = await fetch('https://api.greenfield.lib/v1/books/42', {
  headers: { Authorization: `Bearer ${token}` }
});

if (res.status === 429) {
  const body = await res.json();
  // body.retry_after_seconds is reliable for agents AND humans
  await sleep(body.retry_after_seconds * 1000);
  return retry();
}
import time, requests

r = requests.get(
    "https://api.greenfield.lib/v1/books/42",
    headers={"Authorization": f"Bearer {token}"},
)

if r.status_code == 429:
    body = r.json()
    time.sleep(body["retry_after_seconds"])
    return retry()

Notice three things in the response body that weren't there before: a stable machine-readable error code, a retry_after_seconds integer (agents will parse this; humans will appreciate it), and a docs URL the agent can fetch when it's unsure.

Tip

Always include retry_after_seconds as an integer. Retry-After as a header is fine for humans, but parsers (and agents) keep getting it wrong when it's an HTTP date.

The most common mistake #

Teams put their best error explanations in the prose docs and skimp on the API response. That's exactly backwards. An agent in production never reads your prose. It reads what comes back over the wire.

Watch out

If the only place a recovery hint exists is in your prose docs, treat that as undocumented. The wire is the contract.

Recap #

  • 429 is the user's problem; 503 is the server's. Never blur them.
  • Error descriptions are read by agents, not just humans.
  • Include machine-readable recovery hints (retry_after_seconds, stable error codes, docs URLs) in the response body.
  • Prose docs are for humans; the wire is for everything.
